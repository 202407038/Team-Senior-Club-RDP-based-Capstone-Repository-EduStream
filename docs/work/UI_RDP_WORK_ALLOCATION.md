## 1. 담당별 완료 책임

| 역할 | 책임 |
|---|---|
| 1번·김규환 | 공통 계약·회귀 기반, 통합 검수, 문서/일정 |
| 2번 | 인증·참가/목록 상태·원격 제어 권한 정책·재연결·실행 제한·IP·파일 요청 라우팅 |
| 3번 | 화면 송수신/원격 입력 기술, 모니터·배율 어댑터, 판서 렌더링/공유 |
| 4번·김규환 | 세션 파일 목록·등록/해제·선택 전송/저장·복구 |
| 5번 | 교수자와 학생 UI 제작, 학생 목록/다중 보기/큰 보기, 입력·바인딩·권한/오류 표시 |

각 담당자는 자기 범위의 **구현·테스트·재현/검증 기록·발견 결함 수정**까지 책임집니다. 중간 검토본과 완료본을 구분하고, 알려진 미완료를 숨기지 않습니다. 통합 검수에서 발견한 결함도 해당 담당자가 수정 후 재검증 결과를 제출합니다.

## 2. 역할 경계 (이번 개선에 적용)

### 1번·팀장: 공통 코어와 통합 검수

- Core DTO/인터페이스·상태/오류·테스트 대역을 먼저 제공합니다. 인증/초대 보호 방식·방 비밀번호/무비밀번호 정책·이전 버전 호환을 2번과 확정합니다.
- 공통 계약 결함 수정, 양 앱 기능 조립/통합 검수, 담당별 인수 기준·문서/일정 관리. 교수자 UI 제작은 5번에게 배정합니다.
- 역할이 겹치는 결함은 원인과 책임 범위를 정하고 담당별 수정 결과를 검수합니다.

### 2번: 세션 및 제어 흐름

- 방 참가 인증·초대 전달·자동 재연결, 승인된 참가자 목록/접속/보기·제어 허용 상태를 제공합니다.
- 원격 제어 대상 선택 승인, 한 대상만 제어, 대상 변경/학생 거부/단절/강의 종료 시 권한 회수. 실제 마우스·키보드 주입 엔진은 3번 담당입니다.
- 앱 실행 순서 제한 서비스, 호스트 IP·포트 정보, 여러 네트워크 구분을 맡습니다. UI 배치는 5번이며 양 앱 시작점 연결 위치와 호출 예제를 함께 제출합니다.
- 파일 목록 안내/다운로드 요청을 실제 참가자 신원과 대조해 4번 서비스로 전달합니다. 파일 본문/저장/등록 해제 정책 자체는 4번과 1번 계약에 따릅니다.
- 참가자/권한·라우팅 서비스의 실패 응답과 단위/통합 테스트를 제공하고 해당 결함을 수정합니다.

### 3번: 화면·원격 제어·판서 기술

- 교수자→학생 공유뿐 아니라 학생→교수자 화면과 교수자→선택 학생 입력 경로를 기술 검증하고 기능 단위 서비스/표시 어댑터를 제공합니다.
- 모니터 선택·DPI·해상도, 실제 WDS 맞춤/확대축소 어댑터, 동시에 펼친 학생 viewer 수명과 실제 이벤트 처리를 담당합니다.
- 공유 화면 판서 렌더링, 원래 화면 조작으로 복귀, 표시/숨김/삭제·실행 취소의 동작 엔진 및 학생 수신에서 판서가 보이는지 검증합니다. 도구 모음의 버튼/배치는 5번이 맡습니다.
- 2번의 권한 승인/회수 결과를 실제 연결·입력에 적용합니다. 교수자 화면은 학생에게 항상 보기 전용이며 반대 방향 제어는 별도 승인 상태여야 합니다.
- 신규 양방향 서비스/어댑터는 1번과 파일 경계를 정한 뒤 작업합니다. 5번의 MainWindow/ViewModel 레이아웃 파일을 임의 수정하지 않습니다. 실제 화면·입력·판서의 검증 근거와 실패/종료 회귀를 제출합니다.

### 4번·김규환: 파일

- 파일 선택/드롭에서 호출할 등록·목록·등록 해제 API, 요청 기반 전송, 학생별 진행 상태, 다운로드 폴더 저장/중복 이름/권한·잠금/checksum·취소 회귀.
- 등록 해제/전송 중 경합/원본 변경은 1번 계약으로 고정하고 2번 요청 라우팅에 결과를 제공합니다. 파일 UI는 5번이 서비스 바인딩으로 제작합니다.
- 파일 관련 결함 수정과 바이트/해시·원본 보존 재검증을 담당합니다.

### 5번: 양 앱 UI와 사용자 입력

- 교수자·학생 MainWindow 및 해당 UI ViewModel/컨트롤의 배치·바인딩을 주도합니다.
- 참가 화면/강의 화면 전환, 채팅 Enter·복사, 파일 등록/다운로드 UI, 제어 허용/중단, 학생 개별/전체 펼침과 큰 보기, 판서 도구 모음·버튼/색/굵기 입력을 구현합니다.
- 3번이 제공한 native viewer/판서 어댑터를 UI STA에서 부착·표시하며 화면 기술 엔진 자체를 중복 작성하지 않습니다. 기존 Client RdpViewerService 수정 책임은 기술 변경=3번, 화면 바인딩=5번으로 사전에 파일/커밋을 나눕니다.
- 서버 인증·파일 저장·권한 정책을 ViewModel에 재구현하지 않습니다. 서비스가 미완성인 동안 1번 계약의 테스트 대역으로 화면을 준비하고 실제 서비스 인계 후 연결·사용자 시나리오를 검증합니다.
- UI 잘림·버튼 상태·입력/오류 문구·권한 표시 등 담당 결함을 수정하고 해상도별 결과를 제출합니다.

## 3. 충돌 방지와 계약 선행

- 이번 개선에는 위 배분을 적용합니다. 기존 문서의 교수자 UI/학생 수신 역할 설명과 충돌하면 이 기준을 우선하며, 기존 코드를 무단 이동/삭제하지 않습니다.
- ServerViewModel/MainWindow 등 양 앱 UI는 5번, SessionManager/TCP는 2번, 화면 서비스는 3번, 파일 서비스는 4번, Core는 1번이 소유합니다. 같은 파일을 바꿔야 하면 단일 작성자와 변경 구역/순서를 먼저 정합니다.
- 2번 실행 제한은 독립 서비스로, 3번 native 화면/판서는 독립 어댑터로 제공하며 시작점/컨트롤 부착 위치·호출 예제를 인계합니다. 한 PR에 상대의 서비스/전체 UI를 섞지 않습니다.
- 방 비밀번호와 내부 연결 인증을 혼동하지 않습니다. 기존 평문 TCP에 비밀번호·초대 비밀을 그대로 추가하는 방식은 승인하지 않습니다. 보호된 인증/초대 전달과 교수자 신원 검증 방식은 코드 계약 단계에서 먼저 결정합니다.
- 학생 화면 접기/모두 접기와 입력 제어의 관계, 진행 중 다운로드의 등록 해제, 모니터 전환/세션 종료 시 판서 초기화 등 미세 동작은 9/20 계약표에서 정합니다. UI 시안만 보고 임의 구현하지 않습니다.

| 순서 | 제공자 → 소비자 | 산출물 |

## 6. 검증·게시 원칙

- 커밋은 구현·테스트·문서의 목적별로 나누고 역할별 PR에 주차·검증·미완료를 적습니다. 수정/재검증 결과는 해당 PR에 기록합니다.
- 화면·입력의 실제 방향, 학생 거부·종료·끊김 때 입력 차단, 동시 화면 수와 자원/지연, 원치 않는 화면 재공유를 수동 검증합니다. 비밀번호·초대·학생의 사적인 화면은 기록에 넣지 않습니다.
- 기존 단방향 RDP·채팅·파일·heartbeat·종료 경합·checksum 회귀를 삭제하지 않습니다. 새 권한/상태는 추가 회귀로 검증합니다.
- 이번 승인 범위는 요구사항·이미지·역할·일정 문서의 게시/머지입니다. 새 기능 코드나 설치형/ZIP을 구현 완료로 게시하지 않습니다. 본 작업에서 프로그램 실행 상태도 임의 변경하지 않습니다.
