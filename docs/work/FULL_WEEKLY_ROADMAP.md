# 전체 주차별 로드맵

이 문서는 2026년 11월 1주차까지 기능 구현, 통합 검증, 발표/보고서 준비를 끝내기 위한 전체 기준표입니다.

`STATUS_AND_ROADMAP.md`는 작업자가 빠르게 보는 현재 달과 다음 달 기준 문서로 유지하고, 이 문서는 팀 전체가 공유하는 전체 일정 기준으로 사용합니다. 매주 `STATUS_AND_ROADMAP.md`를 갱신할 때는 이 문서에서 해당 주차와 다음 달 목표를 가져와 반영합니다.

## 검증 기준

이 계획은 아래 자료를 기준으로 다시 검증했습니다.

- 졸작 중간발표 PPT 기준 목표: 교수자 화면 공유, 파일 배포, 채팅을 하나의 강의 흐름으로 제공
- `docs/reference/USER_WORKFLOW_SCENARIOS.md`: 교수자 세션 개설부터 수강생 접속, 화면 공유, 파일 전송, 채팅, 종료까지의 대표 흐름
- `docs/reference/ARCHITECTURE_GUIDE.md`: `Core`, `Server`, `Client` 책임 분리
- `docs/archive/IMPLEMENTATION_PLAYBOOK.md`: 1번부터 5번까지의 역할별 담당 파일과 책임
- 현재 코드 상태: TCP 세션·파일·채팅, WDS 공유/학생 수신과 교수자 진입점, 보조 PNG 경로가 존재. 다중 PC 실사용 인수는 별도 진행
- 현재 테스트 상태: 패킷, 세션, heartbeat, 화면 송신, 파일 전송 roundtrip과 실패 케이스 테스트가 존재

## 완료 정의

11월 1주차 완료는 단순히 코드가 있는 상태가 아니라 아래 조건을 만족하는 상태입니다.

- 교수자 1명과 수강생 2명 이상이 같은 세션에 접속할 수 있다.
- RDP를 기본 경로로 교수자의 동일한 화면을 수강생 2명 이상에게 공유하고, 파일 전송·채팅이 같은 강의 세션에서 병행 동작한다.
- disconnect, heartbeat timeout, 송신 실패, 파일 checksum 실패, 화면 캡처 실패가 로그와 UI 상태로 드러난다.
- 서버와 클라이언트 실행 방법이 README와 실행 가이드에 맞게 검증되어 있다.
- `dotnet build EduStream.sln`과 `dotnet test EduStream.sln --no-build`가 main 기준으로 통과한다.
- 발표 시연 순서, 최종보고서 본문 초안, 주요 화면 캡처, 역할별 구현 설명이 준비되어 있다.
- 11월 1주차 종료 시점에는 기능 구현을 새로 시작하지 않고 문서/시연 보정만 할 수 있다.

## 역할 기준

### 1번. 공통 코어 / 프로토콜

- 패킷 계약, `PacketFactory`, `PacketSerializer`, 공통 상태 모델, 검증 유틸을 담당합니다.
- 서버와 클라이언트가 같은 규칙을 쓰도록 중복 상수와 예외 코드를 `Core`로 모읍니다.
- 각 기능 담당이 임의 문자열이나 임시 상태값을 늘리지 않도록 기준을 제공합니다.

### 2번. 서버 세션 / 네트워크

- `SessionManager`, `TcpServerService`, `HeartbeatService`, 서버 로그와 참가자 상태를 담당합니다.
- join, leave, disconnect, timeout, 송신 실패 클라이언트 제거, 다중 클라이언트 유지 흐름을 안정화합니다.
- 화면/파일/채팅 패킷이 같은 세션 기준으로 흘러가도록 서버 라우팅을 정리합니다.

### 3번. 화면 송신

- RDP 교수자 공유 기능과 연결 수명을 주도하고, 5번과 학생 수신 화면을 연동합니다. 기존 `ScreenCapturer`, `ScreenShareService`, `ScreenPacket`, `ScreenTransferUtility`는 보조 PNG 경로로 관리합니다.
- 실제 프레임 생성, 반복 송신, 시작/중지, fallback, 송신 상태 로그를 안정화합니다.
- 클라이언트 화면 수신 상태와 연결 가능한 송신 결과를 제공합니다.

### 4번. 파일 전송

- `FileDistributor`, `FileReceiver`, `FilePacket`, `FileTransferUtility`를 담당합니다.
- 청크 생성, 메타데이터 검증, checksum 검증, 재전송, 다중 수신, 실패 후 정리를 안정화합니다.
- 파일 전송 결과가 UI 상태와 로그로 확인되도록 결과 모델을 보강합니다.

### 5번. 클라이언트 UI / 수신

- `ClientViewModel`, `MainWindow.xaml`, `SessionClient`, `ScreenRenderer`, 수신 상태 UI를 담당합니다.
- 세션, 채팅, 화면, 파일 상태가 한 화면에서 헷갈리지 않게 보이도록 정리합니다.
- 오류, 대기, 진행 중, 완료 상태가 실제 패킷 결과와 맞게 표시되는지 확인합니다.

각 담당자는 최신 main에서 독립 브랜치로 구현·테스트하고, 팀장이 공통 계약과 실제 실행 경로를 합칩니다. 2·3·5번이 서로의 구현 파일을 수정하거나 상대 브랜치를 먼저 병합할 필요가 없도록 다음 경계를 적용합니다.

| 담당 | 단독 구현 책임 | 주 담당 파일/영역 | 인수인계 결과 |
|---|---|---|---|
| 1번·팀장 | 공통 계약 확정, PR 검토·병합, 서버/UI 조립 및 통합 검증 | Core, 공유 진입점, 로드맵 | 공급자별 계약, 통합 코드, 검증·결함 기록 |
| 2번 | 강의 참가 자격, 참가자/연결 수명, 종료·재접속 정책 | Server의 SessionManager·TcpServerService·HeartbeatService 및 관련 테스트 | 참가 허용/거부 결과, 참가·이탈·종료 이벤트와 정리 API |
| 3번 | 교수자 RDP 공유 엔진 및 공유 측 장애 복구 | Server의 RDP 서비스·컨트롤·관련 테스트 | 공유 시작/중지 API, 학생에게 전달할 연결 정보 생성, 공유 상태/실패 이벤트 |
| 4번·팀장 | 파일 송수신 및 RDP 병행 검증 | FileDistributor·FileReceiver, 파일 테스트 | 크기별 전송·복구 결과와 시연 샘플 |
| 5번 | 학생 RDP 수신 엔진·화면 표시·상태 UI | Client의 RDP 서비스·컨트롤·ClientViewModel·MainWindow.xaml·관련 테스트 | 연결 정보 입력으로 접속/해제하는 수신 API, 상태/실패 이벤트 및 실제 표시 화면 |

- 3번에게 학생 수신 UI까지 맡기지 않습니다. 5번은 단순 화면 배치뿐 아니라 학생 측 RDP 컨트롤/수신 어댑터를 담당합니다.
- ServerViewModel·서버 MainWindow 등 공유 진입점의 최종 버튼/서비스 연결은 팀장이 통합합니다. 각 담당자는 호출 예시와 필요한 변경 위치를 PR에 적습니다.
- 2·3·5번은 Core와 다른 담당 파일, 전체 로드맵을 직접 변경하지 않습니다. 공통 계약 변경 요청과 최소 재현 근거를 PR에 남기면 1번·팀장이 반영합니다.
- 1번이 확정한 WDS 공유·수신 API 및 초대 패킷을 기준으로 개발합니다. 3·5번은 각 PC의 지원/접속 여부를 검증하고 변경 필요 시 팀장에게 근거를 제출합니다.
- 입력에는 강의 세션 ID·학생 ID·연결 시도 ID, 출력에는 연결 정보·상태·실패 원인을 사용합니다. 구체 데이터 형식은 #33 계약을 따르며 민감한 연결 정보는 로그에 남기지 않습니다.
- 상대 구현이 없으면 테스트 대역 또는 최소 호출 프로그램으로 자신의 API를 검증합니다. 이것은 단독 개발 증빙이며 실제 RDP 통합 완료로 계산하지 않습니다.

## 위험 요소와 대응

- 화면 캡처 품질이 낮을 경우: 실제 화면 공유 품질을 우선하되, fallback 프레임과 상태 설명을 시연 대안으로 준비합니다.
- RDP 구현이 늦어질 경우: RDP는 필수 목표로 유지합니다. 9월 13일 구조 검증, 9월 20일 다중 학생 통합, 10월 4일 시연 완료 관문에서 미달 원인과 일정 영향을 기록하고 팀장이 우선순위를 재조정합니다. PNG 송수신으로 완료를 대체하지 않습니다.
- 다중 클라이언트 테스트가 불안정할 경우: 루프백 자동 테스트와 수동 실행 체크리스트를 병행합니다.
- 파일 대용량 전송이 불안정할 경우: 발표 시연은 중형 파일 기준으로 고정하고, 대용량은 검증 항목으로 분리합니다.
- UI 작업이 늦어질 경우: 기능 동작 확인에 필요한 상태 패널을 우선하고, 시각적 다듬기는 QA 단계에서 처리합니다.
- 팀원 PR이 늦어질 경우: 해당 역할의 미완료 항목을 다음 주차 첫 항목으로 올리고, main 반영 여부를 `STATUS_AND_ROADMAP.md`에 표시합니다.

## 사용 방법

1. 매주 시작할 때 이 문서에서 해당 주차 목표를 확인합니다.
2. `STATUS_AND_ROADMAP.md`에는 현재 달과 다음 달 목표만 옮깁니다.
3. 각 역할은 자기 담당 목표를 PR 단위로 쪼갭니다.
4. 주차 종료 전 build/test와 수동 실행 결과를 기록합니다.
5. 완료된 항목은 `STATUS_AND_ROADMAP.md`에서 `----- %완료%`로 표시합니다.
