# 7일 스프린트 상세 구현 가이드

## 1. 문서 목적

이 문서는 현재 프로젝트 상태와 이미 반영된 공통 코어 계약을 기준으로, 개발 팀원 5명이 7일 동안 실제로 구현해야 하는 작업을 상세하게 정리한 스프린트 가이드입니다.

기존 계획보다 작업량을 더 촘촘하게 잡되, 무리하게 “완성품”을 요구하기보다는 다음 조건을 만족하는 것을 목표로 합니다. 이번 버전은 저번 스프린트 문서 대비 작업량을 2배 수준으로 확장하며, 역할 분담은 그대로 유지한 채 각 담당자가 산출물, 검증, 문서 반영까지 책임지는 형태로 운영합니다.

- 세션 흐름이 서버/클라이언트에서 실제로 이어진다.
- 채팅, 파일 전송, 화면 송신이 각각 독립적으로 검증 가능하다.
- UI에서 연결 상태와 수신 상태가 실제 코드 흐름과 연결된다.
- 7일차 시점에 “설명 가능한 데모”가 아니라 “직접 실행 가능한 데모”가 된다.

## 2. 작업 시작 전 공통 규칙

모든 개발 팀원은 작업을 시작하기 전에 아래 순서로 원격 최신 상태를 확인합니다.

```bash
git fetch --all --prune
git status --short --branch
```

권장 순서는 다음과 같습니다.

```bash
git checkout main
git pull --ff-only origin main
git checkout -b feature/<작업명>
```

이 규칙은 선택 사항이 아니라 기본 절차입니다.

이유:
- 이미 머지된 PR을 놓치지 않기 위해
- 브랜치 정리 상태를 최신으로 맞추기 위해
- 오래된 구조 기준으로 개발하는 일을 줄이기 위해

현재 작업 브랜치가 이미 존재한다면 아래를 먼저 실행합니다.

```bash
git pull --ff-only origin <현재브랜치>
```

## 3. 이번 스프린트 목표

### 필수 목표

- 서버에서 세션을 열고, 클라이언트가 참가할 수 있다.
- 참가/이탈/오류 응답이 UI와 로그에 반영된다.
- 채팅 메시지가 양방향으로 전달되고, 서버/클라이언트 UI 양쪽에서 확인 가능하다.
- 파일 전송은 청크 단위로 송신/수신/검증/저장 흐름이 이어진다.
- 화면 송신은 최소한 서버 캡처 -> 패킷 구성 -> 클라이언트 수신 상태 반영까지 이어진다.

### 권장 목표

- 다중 클라이언트 2명 이상 기준으로 세션/채팅/파일 흐름을 검증한다.
- 파일 전송 실패 또는 체크섬 오류 시 UI에 실패 상태가 반영된다.
- 화면 송신 패킷의 메타데이터와 렌더 상태가 로그와 UI 모두에 표시된다.
- 데모 시나리오를 그대로 따라갈 수 있을 만큼 동작 순서가 정리된다.
- 각 역할 담당자가 최소 2종류 이상의 검증 결과를 남긴다.
- 코드 변경과 함께 문서/로그 기준도 같이 업데이트한다.

### 이번 스프린트에서 끝까지 무리하지 않을 것

- 고성능 화면 스트리밍 최적화
- RDP 기반 구조의 최종 확정
- 완전한 재전송/복구 로직
- MessagePack 전환
- 운영 환경 배포 품질

## 4. 5명 역할 분담

### 1번. 공통 코어 / 프로토콜 담당

담당 범위:
- `EduStream.Core`
- 패킷 모델
- 직렬화기
- 공통 유틸
- 에러/응답 코드
- 전송 검증 규칙

이번 스프린트 목표:
- 패킷 계약을 최종 고정에 가깝게 다듬기
- 다른 담당자가 별도 해석 없이 사용할 수 있게 기준을 문서와 코드에 함께 남기기
- 파일/화면/세션 관련 공통 검증 규칙을 코어로 끌어올리기
- 공통 팩토리, 검증 헬퍼, 상수 정의를 한 번에 정리해 중복 구현 여지를 줄이기
- 이번 주 안에 확정할 계약과 다음 스프린트로 넘길 계약을 구분해 표시하기

### 2번. 서버 세션 / 네트워크 담당

담당 범위:
- `SessionManager`
- 서버 세션 개설/종료
- join / leave / ack / error 처리
- 참가자 수 갱신
- 연결 상태 관리

이번 스프린트 목표:
- 세션 흐름이 실제 네트워크 송수신과 연결되도록 만들기
- 참가자 수, 접속 상태, disconnect 처리까지 서버 기준을 안정화하기
- 재접속/비정상 종료/중복 참가 요청까지 고려한 예외 흐름을 추가로 정리하기
- 다중 참여자 기준으로 참가자 목록과 이벤트 로그의 일관성을 맞추기

### 3번. 서버 화면 송신 담당

담당 범위:
- `ScreenCapturer`
- 화면 프레임 생성
- `ScreenPacket` 구성
- 서버 화면 송신 진입점

이번 스프린트 목표:
- 빈 스텁이 아니라 실제 프레임 데이터가 흐르도록 만들기
- 화면 송신 흐름과 패킷 메타데이터를 정리하고, 이후 스트리밍 최적화 전에 검증 가능한 상태까지 끌고 가기
- 캡처 실패, 빈 프레임, 포맷 불일치에 대한 fallback 기준을 마련하기
- 파일/채팅 동시 사용 중에도 화면 송신 상태가 최소한 유지되는지 확인하기

### 4번. 파일 전송 담당

담당 범위:
- `FileDistributor`
- `FileReceiver`
- 파일 청크 전송
- 체크섬 검증
- 저장 결과 처리

이번 스프린트 목표:
- 작은 파일과 중간 크기 파일 기준으로 송신/수신/저장 흐름을 end-to-end로 검증하기
- 실패 시나리오를 최소 1개 이상 고려해 UI와 로그까지 연결하기
- 청크 메타데이터 오류와 체크섬 오류를 구분해 처리하기
- 저장 완료 전/후 상태를 사용자와 개발 로그에서 모두 추적 가능하게 만들기

### 5번. 클라이언트 UI / 수신 담당

담당 범위:
- `EduStream.Client`
- `SessionClient`
- `ClientViewModel`
- 연결/채팅/파일/화면 상태 UI

이번 스프린트 목표:
- 사용자가 지금 무엇을 하고 있는지, 어떤 상태인지, 성공/실패가 무엇인지 UI에서 읽히게 만들기
- 서비스에서 들어오는 결과를 화면 상태와 로그에 반영하기
- 세션/채팅/파일/화면 패널의 정보 밀도를 높여도 읽기 흐름이 무너지지 않게 정리하기
- 서버 응답, 예외, 마지막 성공 결과를 분리된 상태 영역으로 보여주기

- 실제 캡처 프레임 생성 로직 보강
- 캡처 실패 시 fallback 프레임 처리
- `ScreenPacket`에 메타데이터를 정확히 채우는지 확인
- 서버에서 화면 송신 진입점이 재사용 가능하도록 정리
- 송신 시작/중지 시 로그 기준 통일
- 프레임 생성 실패가 연속 발생할 때 최소 상태 표시 유지

5번:
- 화면 수신 상태 UI 보강
- 렌더 상태 문자열, 최근 프레임 정보, 실패 상태 표시
- 파일 상태 패널과 화면 상태 패널이 겹치지 않게 구조 정리
- 마지막 프레임 수신 시각 또는 인덱스 표시
- 화면 미수신 상태와 오류 상태를 구분해 표기

### Day 6. 통합 테스트와 다중 흐름 검증

공통:
- 세션 + 채팅 + 파일 + 화면 흐름을 묶어서 테스트
- 기능 간 충돌 확인
- 문서와 실제 구현 차이 확인
- 시연 순서대로 체크리스트를 작성해 실제 데모 흐름 검증
- 각 담당자가 최소 2개 이상의 재현 로그를 남김

1번:
- 공통 코어 변경이 서비스 계층과 어긋나지 않는지 최종 점검
- 누락된 상수, 유틸, 공통 규칙 보강
- 최근 일주일 머지 내역 기준 누락된 계약 반영 여부 확인

2번:
- 다중 클라이언트 기준 세션 흐름 점검
- disconnect / reconnect / leave 처리 확인
- 서버 로그와 UI 상태가 같은 순서로 보이는지 대조

3번:
- 화면 송신이 파일/채팅 흐름과 동시에 동작하는지 확인
- 최소한 프레임 생성/전송 상태가 무너지지 않는지 확인
- 캡처 실패 후 회복 흐름이 있는지 수동 점검

4번:
- 청크 파일 수신/저장 테스트 반복
- 실패 시나리오 1개 이상 직접 확인
- 중간 크기 파일에서 진행률과 완료 상태 일치 여부 확인

5번:
- UI에서 상태가 모두 읽히는지 점검
- 로그, 상태 문구, 패널 배치, 버튼 활성/비활성 점검
- 데모 진행 중 혼동되는 문구를 짧고 명확한 표현으로 정리

### Day 7. 정리 / PR / 머지 준비

공통:
- 로컬 빌드
- 불필요한 파일 제거
- 문서 반영 여부 확인
- PR 단위 정리
- 이번 주 검증 결과와 다음 주 이월 항목 정리

1번:
- 코어 변경이 다른 담당자 작업과 충돌 없는지 최종 점검
- 공통 클래스/유틸 변경 범위가 과하지 않은지 점검
- 남은 불확실 계약을 다음 스프린트 메모로 분리

2번~5번:
- 기능별로 리뷰 가능한 최소 단위로 PR 정리
- 머지 후 시연 순서대로 기능 점검
- 변경 설명에 검증 방법과 실패 케이스를 함께 기록

전체:
- 시연 가능한 최소 흐름 점검
- 다음 스프린트에서 할 일 분리
- 역할 분담 유지 상태에서 남은 작업량을 재배치하지 않고 backlog로만 이동

## 6. 권장 PR 단위

좋은 PR 예시:
- `feat: stabilize session join and leave flow`
- `feat: add shared file transfer validation rules`
- `feat: add server screen preview packet flow`
- `feat: redesign client session and chat workflow UI`

좋지 않은 PR 예시:
- 채팅 + 파일 전송 + 화면 송신 + UI 전체를 한 번에 넣는 PR

## 7. 이번 스프린트 종료 기준

이번 스프린트가 성공이라고 볼 수 있는 기준:

- 서버에서 세션을 열 수 있다.
- 클라이언트가 세션에 참가/이탈할 수 있다.
- 채팅이 양방향으로 보인다.
- 파일 전송 최소 흐름이 검증된다.
- 화면 프레임 송신/수신 상태가 검증된다.
- README / docs / UML / 코드 간 큰 불일치가 없다.
