# 7일 스프린트 상세 구현 가이드

## 1. 문서 목적

이 문서는 현재 저장소 상태와 이미 반영된 공통 코어 계약을 기준으로, 개발 팀원 5명이 7일 동안 무엇을 구현해야 하는지 상세하게 정리한 스프린트 문서입니다.

이번 버전은 기존 계획보다 작업량을 더 촘촘하게 늘린 버전입니다. 다만 무리하게 "완성품"을 목표로 잡지 않고, 7일차 시점에 다음 조건을 만족하는 실행 가능한 데모를 만드는 것을 목표로 합니다.

- 서버에서 세션을 열 수 있다.
- 클라이언트가 세션에 참가/이탈할 수 있다.
- 채팅 흐름이 보인다.
- 파일 전송 흐름이 보인다.
- 화면 송신/수신 상태가 보인다.
- README / docs / UML / 코드가 크게 어긋나지 않는다.

## 2. 작업 시작 전 공통 절차

모든 개발 팀원은 작업을 시작하기 전에 아래 명령을 먼저 실행합니다.

```bash
git fetch --all --prune
git status --short --branch
git checkout main
git pull --ff-only origin main
```

그 다음 작업 브랜치를 생성합니다.

```bash
git checkout -b feature/<작업명>
```

이 절차는 선택 사항이 아닙니다. 이전 PR을 놓치거나 오래된 기준으로 작업하는 문제를 줄이기 위한 기본 절차입니다.

## 3. 이번 스프린트의 목표

### 필수 목표

- 세션 open / join / leave 흐름이 로그와 UI에 반영된다.
- 채팅 송수신이 서버와 클라이언트 양쪽에서 보인다.
- 파일 전송은 청크 단위로 검증 가능한 상태까지 연결된다.
- 화면 송신은 실제 프레임 생성과 송신 루프가 동작한다.
- 화면 수신은 최소한 상태 문자열과 프레임 메타데이터를 반영한다.

### 권장 목표

- 다중 클라이언트 2명 이상 기준으로 세션/채팅/파일 흐름을 확인한다.
- 파일 전송 실패 1건 이상을 UI와 로그에서 구분해 보여준다.
- 화면 송신 실패 fallback이 로그에 남는다.
- 시연용 체크리스트를 문서로 정리한다.

### 이번 스프린트에서 무리하지 않을 것

- 운영 수준의 고성능 스트리밍 최적화
- 재전송/복구까지 포함한 완전한 파일 전송
- 배포 자동화
- MessagePack 전환
- 최종 아키텍처 확정

## 4. 역할 분담

### 1번. 공통 코어 / 프로토콜 담당

담당 범위:
- `src/EduStream.Core`
- 패킷 모델
- 공통 상수
- 직렬화기
- 공통 검증/변환 유틸

핵심 목표:
- 서버/클라이언트가 동일한 계약을 사용하도록 코어 기준을 고정한다.
- 세션/채팅/파일/화면 패킷 생성과 검증을 공통 계층으로 끌어올린다.

### 2번. 서버 세션 / 네트워크 담당

담당 범위:
- `SessionManager`
- 세션 open / close / join / leave
- 참가자 목록
- 서버 로그
- heartbeat와 세션 흐름 정리

핵심 목표:
- 세션 생명주기와 참가자 동기화를 안정화한다.

### 3번. 서버 화면 송신 담당

담당 범위:
- `ScreenCapturer`
- `ScreenShareService`
- `RdpHost`
- 화면 프레임 메타데이터
- 화면 송신 상태 표시

핵심 목표:
- 실제 프레임 생성과 반복 송신 루프를 안정적으로 정리한다.

### 4번. 파일 전송 담당

담당 범위:
- `FileDistributor`
- `FileReceiver`
- 파일 청크 처리
- 체크섬 검증
- 저장 흐름

핵심 목표:
- 파일 전송의 성공/실패 흐름을 end-to-end로 검증 가능하게 만든다.

### 5번. 클라이언트 UI / 수신 담당

담당 범위:
- `MainWindow.xaml`
- `ClientViewModel`
- `SessionClient`
- 채팅/파일/화면 상태 UI

핵심 목표:
- 사용자가 현재 상태를 이해할 수 있는 UI와 바인딩 구조를 완성한다.

## 6. PR 분리 기준

좋은 예:
- `feat: expand shared packet factory contracts`
- `feat: add continuous server screen share loop`
- `feat: add chunked file receive validation`
- `feat: redesign client session and chat workflow UI`

좋지 않은 예:
- 채팅 + 파일 + 화면 + UI 전체를 한 번에 묶은 PR

원칙:
- 역할이 다르면 PR도 다르게 쪼갠다.
- 구조 변경과 기능 구현은 가능하면 분리한다.
- 문서 PR은 코드 PR과 분리한다.
