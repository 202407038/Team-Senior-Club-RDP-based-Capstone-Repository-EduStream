# 팀 개발 가이드

## 1. 목적

이 문서는 EduStream 팀이 같은 기준으로 브랜치를 만들고, 커밋을 남기고, 리뷰하고, 머지하기 위한 공통 규칙을 정리한 문서입니다.

프로젝트 참여 인원은 총 6명이지만, 현재는 1명을 개발에서 제외하고 최대 5명이 병렬로 작업하는 상황을 기준으로 작성합니다. 실제 가용 인원이 줄어들더라도 규칙은 동일하게 유지합니다.

## 2. 브랜치 전략

### 기본 브랜치

- `main`
  - 항상 빌드 가능한 상태를 유지합니다.
  - 직접 커밋하지 않고 PR을 통해서만 반영합니다.

### 작업 브랜치

- `feature/<name>`
  - 새로운 기능 구현
  - 예: `feature/chat-flow`, `feature/file-transfer`
- `fix/<name>`
  - 버그 수정
  - 예: `fix/client-reconnect`
- `docs/<name>`
  - 문서 작업
  - 예: `docs/collaboration-guide`
- `refactor/<name>`
  - 동작 변경 없이 구조 개선
  - 예: `refactor/session-service-split`

### 브랜치 생성 규칙

작업 시작 전에는 반드시 아래 명령을 먼저 실행합니다.

```bash
git pull --all --prune
```

이후 아래 순서로 진행합니다.

1. 항상 최신 `main`에서 새 브랜치를 만듭니다.
2. 하나의 브랜치에서는 하나의 목적만 다룹니다.
3. 서로 다른 기능을 한 브랜치에 섞지 않습니다.

예시:

```bash
git checkout main
git pull --all --prune
git checkout -b feature/chat-flow
```

## 3. 커밋 메시지 규칙

### 형식

```text
<type>: <summary>
```

### 사용 가능한 타입

- `feat`: 기능 추가
- `fix`: 버그 수정
- `docs`: 문서 수정
- `refactor`: 기능 변경 없는 구조 개선
- `test`: 테스트 추가 및 수정
- `style`: 포맷팅, 네이밍, 정렬 등 비기능 수정
- `chore`: 빌드, 설정, 의존성, 스크립트 관리

### 예시

```text
feat: add chat message packet model
fix: prevent null state in session client
docs: add collaboration workflow guide
refactor: split screen capture service
```

### 커밋 원칙

- 빌드가 깨지는 상태로 커밋하지 않습니다.
- 의미 없는 중간 저장 커밋(`asdf`, `test`, `tmp`)은 금지합니다.
- 한 커밋에는 하나의 목적만 담습니다.
- 문서만 고쳤으면 `docs`, 코드 동작을 추가했으면 `feat`를 사용합니다.

## 4. Pull Request 규칙

### PR 생성 전 체크리스트

- 로컬 빌드가 통과하는지 확인
- 변경 목적이 제목과 본문에 드러나는지 확인
- 불필요한 파일(`bin`, `obj`, 임시 메모 등)이 포함되지 않았는지 확인
- 리뷰어가 이해할 수 있도록 변경 범위를 정리했는지 확인

### PR 제목 작성 규칙

- 커밋 메시지와 동일한 톤을 사용합니다.
- 가능한 한 `feat:`, `fix:`, `docs:` 형식을 유지합니다.

예시:

```text
feat: add UML-based project skeleton for server, client, and core
```

### PR 본문에 꼭 들어가야 하는 내용

- 작업 목적
- 주요 변경 사항
- 현재 단계에서 일부러 미구현으로 남긴 부분
- 검증 방법

## 5. 리뷰 기준

리뷰는 아래 순서로 확인합니다.

1. 빌드가 되는가
2. 책임 분리가 맞는가
3. 기존 설계 문서와 충돌하지 않는가
4. 네이밍과 구조가 다음 작업자를 헷갈리게 하지 않는가
5. 임시 코드가 영구 코드처럼 남아 있지 않은가

### 리뷰 시 중점 확인 항목

- `EduStream.Core`에 서버 전용 코드가 들어가 있지 않은가
- ViewModel이 UI 제어와 비즈니스 로직을 동시에 들고 있지 않은가
- 실제 구현이 아닌 스텁이라면 주석으로 의도가 드러나는가
- 예외 처리 지점이 너무 늦지 않은가

## 6. 코딩 규칙

### 공통 규칙

- C# 기본 스타일을 따릅니다.
- `nullable enable` 전제를 유지합니다.
- 비동기 메서드는 `Async` 접미사를 붙입니다.
- 공개 타입/메서드는 역할이 드러나는 이름을 사용합니다.
- 의미 없는 축약어는 피합니다.

### 주석 규칙

- 코드만 읽어도 드러나는 내용은 주석으로 반복하지 않습니다.
- 설계 의도, 임시 구현 이유, 추후 교체 포인트는 주석으로 남깁니다.
- 팀 내 가독성을 위해 핵심 주석은 한글로 작성합니다.

좋은 예:

```csharp
// 현재 단계에서는 실제 소켓 대신 상태 전이만 검증한다.
```

나쁜 예:

```csharp
// 변수에 값을 넣는다.
```

### UI / ViewModel 규칙

- XAML 코드비하인드에는 최소한의 연결만 둡니다.
- 화면 상태와 사용자 액션은 ViewModel로 보냅니다.
- 네트워크, 파일, 캡처 로직을 코드비하인드에 넣지 않습니다.

### 서비스 계층 규칙

- 기능별로 책임을 분리합니다.
- 세션 관리, 파일 처리, 화면 처리, 직렬화는 각각 별도 클래스로 둡니다.
- 스텁 구현이라도 나중에 실구현으로 교체하기 쉬운 형태를 유지합니다.

## 7. 일일 작업 절차

1. `git pull --all --prune` 실행
2. `main` 최신화
3. 본인 작업 브랜치 생성 또는 갱신
4. 작업 전 담당 범위 확인
5. 구현
6. 로컬 빌드
7. 커밋
8. 푸시
9. PR 생성
10. 리뷰 반영 후 머지

## 8. 충돌 방지 규칙

- 한 명이 작업 중인 파일을 다른 사람이 동시에 크게 갈아엎지 않습니다.
- 구조 변경 PR과 기능 구현 PR을 분리합니다.
- UI 개편과 네트워크 구현을 한 PR에 섞지 않습니다.
- 큰 작업 전에는 담당 파일 범위를 미리 공유합니다.

## 9. 머지 기준

아래 조건을 만족하면 `main`에 머지할 수 있습니다.

- 빌드 통과
- 변경 목적이 명확함
- 불필요한 파일 없음
- README/UML/관련 문서와 충돌 없음
- 리뷰 또는 팀 내부 확인 완료
